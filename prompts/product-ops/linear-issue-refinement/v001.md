# Linear Issue Refinement (Purpose, Scope, and Expected Output)

You are helping refine a Linear issue so that it clearly communicates purpose, scope, and expected output.

**Primary objective:** Rewrite the issue so it is correctly scoped and easy for an engineer or PM to execute without misunderstanding.

---

## Instructions

1. First, inspect the Linear issue itself.
2. If the Linear integration supports it, also explore and incorporate surrounding context automatically:
   - project
   - cycle / milestone
   - parent issue
   - child / sub-issues
   - related / linked issues
   - any closely associated context that clarifies intent
3. Use that surrounding context to determine the role this issue plays in the broader workstream.
4. Then classify the issue as one of:
   - discovery / research
   - design / specification
   - implementation
   - refactor
   - documentation
5. Identify the true purpose of the issue.
6. Rewrite the issue description so it is:
   - correctly scoped
   - aligned to the broader project
   - explicit about what "done" means
   - protected against scope creep

---

## Important rules

- Do not assume this issue is an implementation ticket just because the current wording sounds technical.
- If surrounding Linear context suggests the ticket is actually research, cleanup, or documentation, rewrite it accordingly.
- Preserve useful examples already in the issue, but label them clearly as examples, sketches, or future-state ideas if they are not the required implementation.
- Do not invent project structure or relationships that are not visible.
- If parent/sub-issue/related-ticket context is unavailable, proceed using only what is available and say so briefly.

---

## Required output

1. A short explanation of this issue's role in the broader workstream.
2. A cleaned-up issue type classification.
3. A rewritten Linear issue description, ready to paste, with these sections:
   - Goal
   - Context
   - Scope of Investigation / Work
   - Questions to Answer
   - Deliverable / Expected Output
   - Non-goals
4. A suggested completion comment that defines what "done" looks like.

---

## Style guidance

- Be precise, concrete, and concise.
- Prefer explicit deliverables over vague intent.
- For research/discovery tickets, make the expected artifact extremely clear.
- For implementation tickets, make the shipped behavior extremely clear.
- Avoid adding new scope that is not supported by the issue and its surrounding context.
