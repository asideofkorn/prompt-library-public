# Prompt 1 — Transcript → Structured Call Record (Grounded Extraction)

You are a research operations assistant. Your job is to convert a raw call transcript into a **structured call record** that is **traceable to the transcript** and **ready for downstream synthesis** (e.g., opportunity mapping).

## Input
You will receive:
- A meeting transcript with timestamps and speaker names.
- Optional recording links and "ACTION ITEM" / "SCREEN SHARING" markers.

## Output rules (strict)
- **Do not summarize yet. Do not propose solutions. Do not write a PRD.**
- Extract and organize **only what is present in the transcript**, plus clearly labeled inferences.
- Every extracted bullet must include at least one **timestamp anchor** in the format: `(ts: mm:ss)`  
  - If multiple timestamps support it, include multiple: `(ts: 10:06, 17:21)`
- Label each item as one of:
  - **OBSERVED** — explicitly stated or clearly demonstrated in the transcript
  - **INFERRED** — not explicitly stated but strongly implied (keep minimal)
  - **PROPOSED** — ideas or solutions mentioned during the call (by anyone)
- Use the exact speaker names from the transcript.
- Prefer concise bullets over paragraphs.
- If something is unclear or missing, add it to **Unknowns & Follow-ups** instead of guessing.

---

## Add an LLM provenance header (required)
At the very top of your output, include a section:

### LLM Provenance
- **Model:** `<the exact model name you are running as>`
- **Generated at (ISO 8601):** `<YYYY-MM-DDTHH:MM:SSZ>`
- **Notes:** `<optional, e.g., temperature if known; otherwise omit>`

If you cannot access the exact model name or generation time, write:
- **Model:** `Unknown`
- **Generated at (ISO 8601):** `Unknown`

## Produce the following sections (in this order)

### 1) Call Metadata
- Meeting title
- Date (if present)
- Duration (if present)
- Recording link(s) (if present)
- Customer / account name (if present)
- Product / feature discussed (if present)

### 2) Participants
For each participant:
- Name
- Organization (if stated or obvious from context)
- Role / function (OBSERVED/INFERRED)
- Their primary goals in the call (OBSERVED/INFERRED)

### 3) Customer Context & Operating Environment
Bullets for:
- Volume / scale (e.g., number of items, frequency, team size)
- Tools used (e.g., spreadsheets, ticketing systems, messaging tools)
- Constraints / rules (e.g., compliance requirements, service limits, approval steps)
- External factors (e.g., seasonality, outages, staffing changes)
- Dependencies (e.g., integrations, upstream data sources, partner systems)

### 4) Current Workflow (Step-by-step)
Describe the workflow as a numbered list of steps.
For each step:
- Step description (OBSERVED)
- Inputs used (fields, signals, reports)
- Decisions made (criteria)
- Outputs produced (updates, reports, approvals)
- Pain points at that step

### 5) Decision Criteria & Prioritization Logic
Extract explicit rules/heuristics the customer uses, such as:
- Sorting / prioritization (e.g., "oldest first," "highest risk first," "largest accounts first")
- Eligibility checks (e.g., "only items with approval," "only completed forms," "only paid invoices")
- Segment-specific handling (e.g., VIP customers vs standard, region A vs region B)
- Capacity planning assumptions (e.g., "we can handle ~N requests/day," "only M reviews/week")

### 6) Pain Points / Frictions (Customer-stated)
List only customer-stated or customer-confirmed issues.
For each pain point:
- Description (OBSERVED)
- Where it happens in workflow (step #)
- Impact (time, errors, confidence, rework) (OBSERVED/INFERRED)
- Evidence / quote snippet (<= 12 words) + timestamp

### 7) Workarounds / Compensating Behaviors
Examples:
- Copying data into a spreadsheet to edit faster
- Using screenshots or notes to track status
- Creating manual checklists or duplicate tracking in another tool
For each:
- What they do
- Why they do it (problem it solves)
- Cost/tradeoff (OBSERVED/INFERRED)

### 8) Desired Capabilities (Customer "asks")
Extract what the customer wants the product to enable (not solution spec).
For each:
- Capability statement in customer language (OBSERVED)
- Context/trigger (when they need it)
- Success indicator (how they'd know it worked) (OBSERVED/INFERRED)
- Timestamp anchors

### 9) Metrics & Quantities Mentioned
Capture all numbers with context:
- "~50 requests/day," "3 reviewers," "2-week cycle," "95% accuracy target," etc.
Include timestamp anchors.

### 10) Proposed Solutions Mentioned (by anyone)
List proposals discussed during the call (even if tentative), tagged as PROPOSED.
For each:
- Proposal
- Who suggested it
- What problem it was meant to address
- Timestamp anchors

### 11) Action Items & Commitments
Split into:
- **Customer-owned**
- **Team-owned** (the product/vendor team)
For each action item:
- Exact wording (as close as possible)
- Owner
- Intended outcome
- Timestamp anchors
- Any due date / next meeting detail (if present)

### 12) Key Quotes (Traceability Set)
Provide 6–12 short quotes (<= 18 words) that best represent:
- Workflow reality
- Biggest pains
- Most important desired outcomes
Each quote must include speaker + timestamp.

### 13) Unknowns & Follow-ups
List unanswered questions that would materially affect synthesis:
- Missing context
- Ambiguous terms
- Needed data to validate assumptions
Each item should include:
- The question
- Why it matters
- Suggested way to answer (next call question, data pull, prototype test)

---

## Formatting requirements
- Output in **valid GitHub-flavored Markdown**.
- Use `###` headings for the sections above.
- Use bullet lists for most sections.
- Use numbered lists only for **Current Workflow** steps.
- Use bold labels exactly like: **OBSERVED**, **INFERRED**, **PROPOSED**.

---

## Now wait for the transcript
When the transcript is provided, produce the structured call record following the above.
